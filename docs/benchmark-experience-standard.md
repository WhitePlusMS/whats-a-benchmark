# 评测体验设计与验收标准

本标准用于后续逐项优化 benchmark 的目录入口和详情体验。目标是让读者看见一项真实任务，理解模型收到什么、需要完成什么、交付什么，以及结果如何检查。

## 可运行的参考样板

- Terminal-Bench 4.0：`/benchmarks/terminal-bench-4/`。保留用户认可的首屏、四类任务切换、步骤图解、动效、原题联动与紧凑来源列表。
- SWE-bench Verified：`/benchmarks/swe-bench-verified/`。四个真实案例使用不同的问题图解，并连接下方来源片段和原题；样板已完成程序与本机浏览器检查，仍需用户实际体验后反馈。
- 对应实现分别在 `src/components/TerminalBenchPilot.vue`、`src/components/SweBenchPilot.vue`；共同视觉规则在 `src/styles/pilot-common.css`。参考样板的阅读节奏和质量，不把代码、内容或四步结构机械复制到每个评测。

## 一项评测应怎样呈现

1. **首屏有明确入口。** 用该评测自己的任务说明告诉读者在测什么，并提供查看真实任务和评分方式的入口；保留比较等既有功能。
2. **任务成为视觉中心。** 选择可核验的真实题目或记录，按该任务的性质组织过程。模型评测、编程任务、机器人任务和指数可能需要不同的图形、媒体或步骤；不要只增加一组文字卡片就算完成。
3. **图形对应题目。** 图解、动画或媒体应帮助理解输入、关键关系、交付物或验收；示意图要标明示意，原始片段应能追溯到具体来源。缺少附件、补丁或模型运行记录时明确说明，不伪造。
4. **保留原文和证据。** 允许从概览进入原题及来源；多个案例的上方图解和下方原题使用同一选择状态，刷新和分享链接应恢复正确题目。没有原题访问权限的条目应说明可获取的资料和限制。
5. **有节制地使用动效。** 切换应说明步骤或状态变化，尊重 `prefers-reduced-motion`；桌面与手机都能操作，键盘焦点清楚，深浅主题均可阅读。
6. **来源紧凑可查。** 沿用 `src/styles/detail.css` 的参考资料索引，保留编号、锚点高亮和展开的同页定位；不要恢复成占满页面的大卡片。

不要把单个模型或厂商成绩当作页面主角。引用成绩时要标记来源与比较条件，不把题目阈值、示范视频或示意图说成模型成绩。

## 执行与完成条件

- 工作单位是 benchmark ID，目录中的模型和具身条目都要覆盖；从当前目录重新盘点，不把旧快照数量当成永久范围。
- 逐个核对任务版本、样例和许可；复用现有样例查看器、来源与 URL 状态。确有共性时提炼小组件或样式，不复制整页代码，也不牺牲每项任务的差异。
- 内容、页面结构、视觉和交互都要检查。若只完成资料整理，应如实标记内容阶段完成，不宣布整页体验已达标；缺乏可公开材料的条目记录缺口并保留官方入口。
- 每项更新 `UPDATE_LOG.md`，运行类型检查及与改动相符的内容校验、测试和构建；对实际页面检查步骤切换、引用、桌面与手机、深浅色、键盘及减少动态效果。云端无法完成浏览器检查时如实标记待本机验收。
- **每完成一个 benchmark 单独提交一次 Git**。共享代码仅随相关评测的实现提交；检查暂存内容，不混入其他条目或用户已有工作。
- 当前 SWE-bench 样板尚未经过用户评价；先让用户查看两个样板，再据反馈继续扩大。此前云端的 SWE-bench、Terminal-Bench 和 RoboQuest 提交提供了有价值的资料整理，不应因为重做视觉而丢弃；其中 RoboQuest 仍需按本标准完成页面体验。
