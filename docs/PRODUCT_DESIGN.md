## 1. 产品承诺

一句话：看懂 AI 发布会里的每一个评测名字。

用户从一张模型成绩表进入网站，应该可以完成以下过程：

1. 搜到一个不认识的评测名字。
2. 用十几秒知道它主要测什么。
3. 打开一个有出处的任务，理解模型实际要做什么。
4. 看懂指标、版本与运行条件，知道这个分数能说明什么。
5. 找到官网、论文、数据和官方榜单，继续深入。

网站以评测知识为核心。首版链接官方成绩和报告，不维护跨模型成绩数据库。增加“评测对照”功能，用于比较几套评测的测试内容，不为模型制造综合排名。

2026-09-24 用户确认名称为 what's a benchmark?，中文名“到底测什么？”。

## 3. 页面结构与主要交互

### 首页：直接进入图鉴

顶部：品牌标识、全部评测、入门指南、关于与来源规范。

主标题：“看懂分数之前，先看懂考题。”

说明：“这些评测究竟在考什么？看看真实任务、评分方法，以及那些容易混淆的版本。”

首屏以搜索为中心，输入提示为“搜索名称、能力、发布方，例如 SWE-bench、数学、OpenAI”。支持常见别名和中英文能力词，优先展示名称精确命中，再展示名称包含和解释匹配；首版使用本地检索。

搜索旁设置“粘贴多个名称”入口：按换行、逗号和分号拆分用户输入，再匹配规范名称与别名；返回已识别、存在歧义和未收录三种结果。出现歧义时展示候选条目供选择。首版不读取截图，不用大模型猜测未收录名称。

首屏下方是能力分类与卡片列表，不设置占屏的大幅宣传图。初始排序采用明确标注的“编辑精选”，其他排序包括名称和资料更新日期；没有访问量数据时不显示“热门排行”。

筛选包含能力方向、发布方、样例查看方式和条目类型；活动筛选可一键清空，结果数量随筛选变化。桌面端采用左侧筛选与三列卡片，移动端采用顶部筛选抽屉与单列卡片。

### 卡片：30 秒认识一个名字

卡片展示的固定信息顺序：

1. 官方 logo（有合适资源时）或本站统一的类别图标。
2. 英文正式名称与简短中文说明。
3. 一句话“它考什么”。
4. 最多三个标签，例如“软件工程 / 修复仓库问题 / 自动测试”。
5. 发布方、具体版本、样例状态。
6. “看题目”“了解评测”“加入对照”入口。

示意内容：

```text
┌──────────────────────────────────────┐
│ [代码图标] SWE-bench Verified         │
│ 在真实代码仓库中解决软件问题           │
│                                      │
│ 给模型一个 issue，看看它能否修改代码   │
│ 并通过对应测试。                      │
│                                      │
│ 软件工程   人工核验子集   自动测试      │
│ [发布方]              [样例查看状态]   │
│ 看题目 →          了解评测   ＋对照     │
└──────────────────────────────────────┘
```

以上是版式示意，方括号内容不是已核实的数据。不在卡片上堆模型得分、题库字段和长段论文摘要。

### 详情页：先解释，再展示证据

详情有独立链接；从目录返回时保留搜索、筛选和滚动位置。“看题目”直接定位到样例区。

| 顺序 | 区块 | 用户获得的信息 |
| --- | --- | --- |
| 1 | 官方定义 | 忠实中文概述、模型实际执行的任务及本段官方依据 |
| 2 | 任务协议 | 输入、预期输出、执行环境和可比条件 |
| 3 | 数据与使用边界 | 规模、split、字段、文件、访问门槛、许可与复用范围 |
| 4 | 真实样例 | 允许转载的官方记录，或不能转载/未公开的具体原因与官方入口 |
| 5 | 评分方法 | 指标定义、数值方向、版本和运行条件对可比性的影响 |
| 6 | 版本与相关评测 | 子集、改编、扩展、不同年份或相关评测的区别及关系证据 |
| 7 | 官方资料 | 按定义、论文、数据、代码、访问、榜单等角色整理的原始来源 |
| 8 | 模型发布资料中的引用 | 厂商模型卡或发布报告对该评测的引用，与 benchmark 官方资料分开 |

正文以中文解释为主，保留英文正式名和关键术语。每项具体事实关联来源；本站的类比、翻译和解释单独标识。题量必须注明所属版本或 split；不能从全量题数推导某次评测实际用了多少题。

### 样例浏览器：这个网站的主要特色

桌面端采用左侧题目、右侧解读；小屏幕上下排列。每个可转载条目最多选择 6 个具有代表性的官方样例，不追求把完整题库放进网页。

样例区提供“读题模式 / 原始格式”切换。读题模式适合初学者，原始格式展示官方字段、文件结构或实际数据片段；不存在统一 JSON 原格式。

| 任务类型 | 读题模式 | 原始格式 |
| --- | --- | --- |
| 选择题 | 题干、选项、展开答案、考查点 | 官方 CSV / JSON 等记录的实际字段 |
| 数学或推理题 | 题目、输入图示、展开参考答案 | 原始题面与答案字段；翻译不覆盖原文 |
| 代码题 | 问题说明、输入输出、可公开测试 | 官方记录或源文件片段 |
| 仓库修复任务 | issue、仓库、目标、评分逻辑 | 任务元数据、相关文件和官方链接 |
| 图像/视频任务 | 原始媒体或官方入口、问题 | 媒体字段、问题字段、公开答案 |
| Agent 环境任务 | 任务目标、可用工具、完成标准 | 任务说明、目录和测试入口 |

参考答案默认折叠。只展示官方公开的答案或评分标准；不补写伪装成官方解析的推理过程。可本地判断的客观题可以提供“选一个答案看看”，这仅是阅读辅助，不给访问者生成能力分数。首版不在浏览器执行代码或运行评测环境。

每个样例保存：来源链接、原始 ID（有则填写）、版本/split、选取说明、转载依据、是否裁剪、是否翻译、核验日期。不同来源的题干、答案、测试脚本不能拼成一个看似官方完整的原题。

样例状态明确区分：站内真实样例、官方入口查看、申请后查看、原题限制公开、题目未公开、许可待核实、样例尚未核实。只有来自官方真实记录且满足公开展示边界的内容计入站内样例数量。

BrowseComp、GPQA 等已发现有避免公开转载题目的要求。此类条目只解释任务结构并提供官方入口；不把原题藏在构建文件、JSON、HTML 注释或图片中。具体依据见 [资料核验记录](./RESEARCH_NOTES.md)。

### 版本关系：回答“这个名字和那个有什么关系”

采用有文字说明的关系列表，而非复杂交互图谱。关系类型包括：版本、子集、改编、扩展、仅相关。每条关系都有一句“具体改了什么”和来源。

厂商相关内容按实际对象归档：

| 情况 | 收录方式 |
| --- | --- |
| 厂商新建独立任务集或评测 | 正常建立评测条目，标记发布方及公开程度 |
| 从现有题库选了一个子集 | 建立有出处的子集条目并关联原评测 |
| 修改任务或评分形成衍生评测 | 建立独立条目，说明与原评测的差异 |
| 同题库换提示词、工具、预算或采样次数 | 放入运行配置/报告说明，不制造新 benchmark |
| 厂商只披露内部评测分数或方法摘要 | 建立“内部评测，资料有限”的条目，缺失字段明确留空 |
| 名称相似但找不到关系证据 | 只建立“相关”导航，不声称派生关系 |

“厂商发布”不是可信度评级，也不等于不公开。评测发布方、成绩报告方和被评模型分别记录。

### 对照页与入门指南

允许选择 2–3 个评测，横向对照“测什么、任务形态、题库/环境、评分规则、版本、样例与来源”。移动端支持表格横向滚动。不给不同 benchmark 的分数画混合雷达图。

入门指南控制为六个短主题：benchmark 和榜单的区别；正确率/通过率/对战评级；pass@k 的尝试次数；工具和推理预算；题库污染与饱和；为什么高分不等于所有实际任务都好用。具体解释需在编写内容时逐项引用可靠来源。

## 4. 视觉语言

整体是“可阅读的技术图鉴”：暖白底、深色文字、靛蓝强调，少量彩色能力标签。采用细边框、适量留白、轻阴影和清晰的文字层级。

| 项目 | 设计方向 |
| --- | --- |
| 背景/卡片 | #F6F7FB / #FFFFFF |
| 正文/强调色 | #172033 / #4F46E5 |
| 字体 | 系统中文无衬线；代码与字段用系统等宽字体 |
| 布局 | 内容最大宽度约 1360px；桌面三列、平板两列、手机一列 |
| 标识 | 本站原创书页/坐标组合标识；官方 logo 有依据地使用 |
| 无 logo 的评测 | 统一类别图标与名称，避免伪造官方徽标 |
| 动效 | 聚焦、筛选和展开的短过渡；尊重减少动态效果偏好 |
| 夜间模式 | 首版先保证浅色阅读体验，后续按实际使用反馈补充 |

能力标签既有颜色也有文字。正文对比度、键盘焦点、答案折叠按钮语义和移动端触控区域都纳入验收。卡片中的操作按钮与详情链接分别实现，避免按钮嵌套和键盘交互冲突。

## 5. 内容收录与持续更新

首批目标为 40 个左右有解释价值的条目，最终数量由逐项来源核验决定。以覆盖不同任务形式、能力方向和易混淆版本为先，不为了凑数填写未经核实的介绍。“所有 benchmark”作为持续扩展方向，不作为一个可以一次完成的封闭清单。

以下只是待采集候选，不表示已核验或全部确定纳入。已完成的少量代表性核验单列在 RESEARCH_NOTES.md 中。

| 能力入口 | 候选例子 |
| --- | --- |
| 知识与专业问答 | MMLU、MMLU-Pro、GPQA、GPQA Diamond、HLE、SimpleQA、C-Eval、CMMLU |
| 数学与抽象推理 | GSM8K、MATH-500、按年份区分的 AIME、FrontierMath、ARC-AGI、OlympiadBench |
| 编程与软件工程 | HumanEval、MBPP、LiveCodeBench、SWE-bench、SWE-bench Verified、SWE-bench Pro、SciCode |
| 搜索、工具与任务执行 | GAIA、BrowseComp、BFCL、tau-bench、tau2-bench、Terminal-Bench、OSWorld、WebArena |
| 图像、文档与视频 | MMMU、MMMU-Pro、MathVista、DocVQA、OCRBench、Video-MME |
| 长文与长对话 | LongBench、LongBench v2、RULER、MRCR |
| 指令遵循与对话偏好 | IFEval、MultiChallenge、MT-Bench、AlpacaEval、Arena 类评测 |
| 真实工作任务 | GDPval 及有公开依据的其他厂商任务评测 |

主分类只是入口，条目可以有多个能力标签。采用开集收录：文本、视觉、音频、视频、代码和工具任务都可以进入，不为分类齐全而填入假数据。

新增一条的必要信息是：正式名称、解释、具体能力、任务形态、发布方、来源、指标含义、版本范围、样例可获得状态。找不到发布日期、准确规模或授权时填未知，不猜测。

维护过程：发现候选 → 找原始来源 → 核实版本与关系 → 核实样例展示条件 → 编写中文解读 → 复核 → 构建发布。来源优先级为项目官网、论文、官方仓库、官方数据卡；媒体只作为发现线索。

首版使用仓库文件编辑；提交时运行数据检查和构建。每次发布更新核验日期和变更记录。自动发现新评测、定时抓取、用户投稿后台、站内 AI 问答均不进入首版。

## 6. 技术方案

采用 Vue 3 + TypeScript + Vite + Vue Router + vite-ssg + 原生 CSS。图标使用少量 SVG；数学题确有公式需求时引入 KaTeX。通过显式类型检查、内容校验和静态构建得到可托管产物。

选择构建时生成页面，是因为读者会搜索和分享某个具体评测名。生成真实的详情页 HTML，兼顾独立链接、刷新访问和正文可被读取；运行时仍只有静态 HTML/CSS/JS，不需要常驻服务。技术依据见 [静态架构决策](./adr/0002-static-pages.md)。

| 层次 | 职责 |
| --- | --- |
| 类型化本地内容 | 条目、来源、指标、关系及样例元数据 |
| 构建校验 | 唯一 ID、关系引用、来源字段、样例状态与文件一致性 |
| 页面组件 | 图鉴、详情、对照、指南 |
| 样例组件 | 按任务类型显示题目和实际格式 |
| 本地检索 | 名称/别名/中文能力词检索与筛选 |
| 静态构建 | 生成所有已发布条目的 HTML 和静态资源 |
| Pages 发布 | GitHub Actions 构建并发布静态产物 |

首版不需要后端、数据库、登录、Pinia 或在线评测 API。当前数据集中于一个有类型约束的 TypeScript 目录文件，固定模板与类型约束保证维护一致；大量原始题面/文件作为独立静态资源，不全部塞进首页包。事实、来源和样例分字段保存，避免在组件中硬编码文案。

建议目录：

```text
src/
  components/        # 卡片、筛选、样例、出处、关系列表
  views/             # 图鉴、详情、对照、指南
  content/           # 类型化目录、样例清单与发布资料
  types/             # 条目、来源、样例的类型
  composables/       # 检索、筛选、对照选择
  styles/            # 颜色、字体、响应式布局
public/
  samples/           # 经核验允许公开的样例资源
  logos/             # 有来源的标识资源
scripts/             # 内容校验和构建辅助
```

内部路由如 /benchmarks/swe-bench-verified/，通过数据显式枚举构建路径，以 nested 目录形式生成 index.html；配置项目仓库对应的 base，生成 sitemap、页面标题、描述与 404 页。未知路径显示明确的未找到页面。

样例大文件在进入详情或打开样例后加载；网络加载失败保留说明和原始来源入口。访问不依赖 Hugging Face/GitHub 接口实时成功。搜索结果和正文可以使用本地快照；来源内容变化通过维护更新反映。

检索与筛选条件放在 URL 查询参数中，对照最多保存三个条目 ID。只在浏览器阶段读写本地状态；静态生成期间不直接访问 window、localStorage 或 DOM。

具体依赖版本在实施时根据官方兼容范围选择并锁定，本轮不预写未经安装验证的版本号。

## 7. 验收标准

1. 新用户搜索 GPQA、SWE-bench、AIME 等名称，能理解其用途并定位来源。
2. 每条正式内容有中文用途说明、评分解释、发布方来源、具体版本和样例状态；未知字段清楚显示。
3. 可站内展示样例有原始链接/记录标识，原题、翻译、裁剪与格式示意可区分。
4. 不公开样例不会出现在任何发布资源中；页面提供可行的官方阅读入口。
5. 用户能说清两个名称是子集、衍生、不同版本还是仅测试配置不同。
6. 搜索、筛选、批量名称识别、对照、答案展开、外链与返回状态经过真实浏览器操作。
