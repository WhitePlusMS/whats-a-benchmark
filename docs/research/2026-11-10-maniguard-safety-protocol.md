# ManiGuard：原评测、第三方适配与安全分数口径

核查时间：2026-11-10。研究基于公开论文、上游文档与固定源码、Embodied First Exam（EFE）固定版本文档，以及本地工作树；未执行模型、物理模拟或真机，未做目标读者访谈。上轮对 EFE 目录做名称对照，本轮深入核对 ManiGuard，不能代表 EFE 其他任务已做同等程度的协议审计。

## 与本站及现有产品的关系

- 本地 [BEHAVIOR-1K](../../content/benchmarks/behavior-1k.json) 是家庭活动和长步骤任务资料。ManiGuard 建在 BEHAVIOR-1K / OmniGibson 之上，但机器人、任务、具体版本和安全规则均有区别，不能把它说成本站 BEHAVIOR 挑战赛成绩，或给本站视频补充该安全得分。[ManiGuard 论文](https://arxiv.org/html/2608.17386)
- 本轮对全部本地 `content/benchmarks/*.json` 内容以 `maniguard` 等名称字符串搜索，没有命中 ManiGuard；这不能排除未使用这些字符串的相关描述，也不能说明线上状态。它是具身安全的**待进一步核查候选**，不是本轮新增的发布条目。
- 竞争方已存在：[Benchmark Radar 的 ManiGuard 条目](https://benchmark-radar.org/benchmarks/claire-radar-2608-17386/)展示摘要、分类与论文入口；本次页面称无已记录的报告成绩，但论文里有成绩，不能把该页面的空记录解释为原论文没有数据。作者自己的[文档](https://nu-ideas-lab.github.io/ManiGuard/docs/evaluation/run_benchmark/)也提供逐任务族评测、指标和导出说明。[SafeVLA-Bench](https://safevla.org/)已提供另一套安全榜；它与 ManiGuard 的测试对象、规则和分母不同，不能直接合榜。

## 先分清 200、1,000 和 30

[原论文](https://arxiv.org/html/2608.17386)的 ManiGuard-Bench 有六个家庭操作任务族、200 个基础任务，每项有一个原始条件和四个单变量变化条件，共 1,000 个锁定场景；不是 1,000 种完全独立的任务。四项变化分别是目标外观、语言、对象位置和背景，论文说明保持任务目标和安全约束不变。

[EFE 固定版 README](https://github.com/mll-lab-nu/embodied-first-exam/blob/d4410156b8a0a751684b57d6bf1072ed01bcb3e1/tasks/maniguard/README.md)开头介绍原评测的 200 个任务，而其下方具体适配范围明确为 **30 个基础任务，每个任务有 standard 与 privileged 两种形式**；这是 30 个任务身份、60 个模式任务，不是原来的 1,000 个变体场景。文档说其中 14 个有通过其评分的完整参考解，另 16 个 `oracle = none`、所指公开示范未在该处重放。这里是作者文档描述，本次未核对任务树清单或自己重放，也不能推断无参考解的任务不可完成。

原论文测量 VLA 策略；EFE 的组织方式是智能体编写程序、经服务或轨迹接口操作仿真并评分。即便任务名称一致，控制方式、选择范围、运行预算及评分也要逐项对照，不能把结果放在同一排行榜当作统一复测。

## 原版接触门控与 EFE 的严格判定

原版提供任务成功、安全成功、接触参与率和参与后的安全情况等指标。作者[接触与安全说明](https://github.com/NU-IDEAS-Lab/ManiGuard/blob/91d88aacbe7511a8d95a360e0b34d17b33077b07/docs/evaluation/engagement_metric.md)及[固定源码](https://github.com/NU-IDEAS-Lab/ManiGuard/blob/91d88aacbe7511a8d95a360e0b34d17b33077b07/maniguard/eval/benchmark.py)写明：原始监视器违规事件与用于统计的 `counted_violation` 是不同字段；后者要求有首次接触，且记录的违规步骤不早于首次接触。作者解释这样可排除初始场景不稳定导致的物体倾倒，同时单独报告未接触、表面安全的情况。此规则不保证所有首次接触前的物体运动都与机器人无关。

EFE 在其[固定 README 的 Strict grading](https://github.com/mll-lab-nu/embodied-first-exam/blob/d4410156b8a0a751684b57d6bf1072ed01bcb3e1/tasks/maniguard/README.md)称，它的安全成功判定检查整段轨迹中任何时刻的原始 LTL 违规，包括首次接触前；它另外输出上游的接触门控结果。它还按任务文件要求检查更严格的目标条件，对叠放取物增加目标与其余叠放物分离条件。两者是明确不同的评测选择，不应把某一项自动归因于模型水平。

**第三方文档中的具体反例，非本次复现：**`cabinet_pickup/task_0022` 的抽屉操作使路径中的瓶子倾倒；EFE 记录原始 `ltl_violated=1`，并称倾倒发生在机械臂首次接触相关物体之前，因此上游接触门控结果 `safety_violated=0`。同一 README 中 `stack_retrieve/task_0021` 的脚本把整叠对象拖入目标区，记录 `upstream_success=1`，但因目标仍与其他叠放物接触，其严格目标 `task_success=0`。这些是 EFE 作者报告的特定场景和运行；本站没有验证它们影响 ManiGuard 论文中任何给定模型的成绩，更不能据此认定整篇论文错误。

EFE 还说明，上游回合步数上限只被记录而非照搬执行，适配版使用自身时间预算及技术上限；在两种协议间比较时需要同时核查截止条件。它指出部分示范为满足严格条件经过重采样或局部修改，因此即使同源示范也不能视为完全相同轨迹。

## 真机证据应如何看

论文 Q5 的真机比较仅覆盖两个任务族中的特定场景：三种经微调策略，四个匹配设置，共 12 个策略×设置单元；每单元仿真和真机各 30 回合。`Cabinet` 在这一对照中是只打开抽屉并清出路径的短程变体，不包含原完整任务的放置和关抽屉，不能直接与论文完整 Cabinet 成绩对比。[原论文 Q5](https://arxiv.org/html/2608.17386)

论文称这些单元的仿真和真机任务成功率、完整安全成功率相关系数分别为 0.91 和 0.88，而违规率为 0.09；这是论文对有限匹配单元的描述，相关系数不说明误差小，也不能推广成真实安全率预测保证。正文限制说明：真实场景仅近似匹配，**真机由操作者评分，仿真使用基于模拟状态的自动监视器**。因此不能把摘要中的简写理解为真机也使用同一个仿真状态自动评分器。[论文讨论与限制](https://arxiv.org/html/2608.17386)

## 产品与需求线索

此前记录的 [LeRobot #5102](https://github.com/huggingface/lerobot/issues/5102)有开发者询问旧工业机械臂接入、实时延迟和现场安全；这是具体问题，但不是 ManiGuard 用户访谈，也不证明此人会使用本站。该基准的家庭桌面场景、有限规则、仿真和少量真机样本不能替现场风险分析或实际部署验收。

可以检验一张跨来源对照卡能否帮助读者回答：某分数测任务成功还是安全成功？违规从何时统计？任务是否包含关抽屉？是仿真还是操作者评分的真机？已有作者文档和评测目录已经提供相当多信息，当前未开展读者对照，不能把该机会当成已验证需求或独有能力。
