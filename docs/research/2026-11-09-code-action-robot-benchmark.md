# 代码控制机器人的评测与真机使用线索

核查日期：2026-11-09。范围为当前本地工作树、公开论文、项目页与一条 GitHub 讨论；没有运行仿真或真机，未验收交互、逐条复算成绩或穷尽互联网。

## 本站已收录：CodeActionBench

[本地条目](../../content/benchmarks/codeactionbench.json)与 [RoboTwin 2.0](../../content/benchmarks/robotwin-2.json)建立基础环境关系：模型依据 RGB 观测等信息生成、执行和修订机器人代码，由受限接口执行并用物理状态验证结果。条目已有任务示意图、任务样例和 `lift_pot` 单次官方执行记录；该记录是仿真而不是现实机器人实测，本轮没有播放视频或复验数值。

[官方论文](https://arxiv.org/html/2609.33807)称，25 个任务各固定一个场景实例、每个配置尝试三次，9 种配置合计 675 次。重复尝试不是 75 个不同的任务或场景；研究者明确未测试迁移到实体机器人。[官方页面](https://codeactionbench.org/benchmark)已有模型成绩、任务覆盖、用时、调用、轨迹和 Arena 对照；完整结果及[仓库](https://github.com/lyhkk/CodeActionBench)的完整轨迹数据仍标“coming soon”。因此信息图、任务解释、榜单、部分过程展示已经存在，不能作为空白功能。论文说明没有完成声明可能由预算终止造成，不应一律计为模型错误判断。

## 真机结果如何读

[Agent as Policy 论文](https://arxiv.org/html/2609.12541)称使用 YAM 六关节机械臂，按预设场景、预算与成功条件评测，检查实体结果及视频。比如四组零件装配报告 **8/10**；其 37.2 分钟平均值只统计成功的 8 次，不能直接当作全部 10 次的平均耗时，也不能据此声称其他机器人或零件达到同样效果。

该团队的 [Hugging Face 数据卡](https://huggingface.co/datasets/Agent-as-Policy/agent-as-policy)描述 162 条真机试验记录，含模型、框架、动作、耗时、成本相关 token、结果来源和智能体自述等字段；162 是数据卡所列所有评估试验，不能当作上面单个任务的试验数。页面给出逐条查看入口，但本次未下载完整数据、逐项核实标签或实际播放。数据卡标 CC BY 4.0、代码标 Apache-2.0，其他第三方资产权利仍依对应文件和来源核查。

## 一条使用者问题

在 [项目 issue #1](https://github.com/agent-as-policy-2026/agent-as-policy/issues/1)，提问者问怎样把项目用于自己的机械臂。贡献者当时答复当前支持 YAM、同型号需更新相机标定文件，并表示会发布其他机械臂的适配指南；此为 2026-09-16 的回复，不证明后来一定发布指南或目前仅支持 YAM。本次没有实际连接机器人或查证提问者后续适配是否成功。

这是一个具体的“从看分数到自己的硬件能否运行”的信号，不是用户访谈、付费证据或行业规模。本站可能帮助读者找到模型、控制接口、机械臂、测试条件和原始资料，但不能仅靠评测介绍替代硬件接口、相机标定或真机验证。现有 [CanIEmbody](https://caniembody.pages.dev/)等也尝试维护策略与硬件的证据矩阵，见[需求台账](2026-11-09-embodied-demand-ledger.md)。

## 本站同一评测的提交者问题与执行条件

- [CodeActionBench issue #1](https://github.com/lyhkk/CodeActionBench/issues/1) 中，一名开发者表示想在官方任务、D0 工具、场景种子、预算和验证器不变的条件下提交自定义 Codex 运行框架，询问应使用哪个冻结版本及 manifest、自定义框架如何以独立系统身份提交、是否有包含轨迹和媒体清单的示例归档。本次读取时 issue 显示开放且未见答复；其身份、后续状态与是否会使用本站未知。
- [官方页面](https://codeactionbench.org/benchmark)已有一般提交步骤：按冻结版本运行，打包运行身份、验证结果、轨迹和媒体清单并附校验值，再提交 issue。一般流程已经存在；上面这位提问者所问的具体版本、自定义框架身份与示例归档，不能根据这些概述替维护者作答。
- [官方论文附录](https://arxiv.org/html/2609.33807)说明各配置使用同一场景 seed，但模型采样 seed 不固定；每项任务的三次尝试发生在同一固定场景。因此保存“seed”时要区分场景和模型采样，不能误写成所有随机性均已固定。预算内的仿真执行时间也排除模型推理和服务等待，不能直接当真实工位端到端耗时。
- 当前[官方仓库](https://github.com/lyhkk/CodeActionBench)已有运行代码、安装和扩展文档；完整轨迹、观测图像及视频的数据包仍标为待发布。本次未执行代码，不能从代码存在推断完整材料或最终提交路径均已验证。

相关的另一工具 [CaP-X issue #33](https://github.com/capgym/cap-x/issues/33) 与 [#32](https://github.com/capgym/cap-x/issues/32)由同一报告者提出：前者称权重加载失败后服务仍可能启动，后者称感知请求失败可能被转换为空检测；两帖都给出候选修复和作者自报的 CPU 模拟测试，并说明真实服务或完整仿真未验证。本次未复现、未确认合并状态，不推断 CodeActionBench 或本站存在同样问题，也不能把两帖当两位独立客户。

对本站而言，针对一个真实问题把**运行框架身份、固定场景与随机性、预算、提交制品及未公开内容**关联到原始文档，值得做读者对照测试；这属于可检验假设，不意味着资料站能够排错、已满足该提问者需求或拥有付费客户。
